三、功能兼容性

3.1 接口返回：逐字段一致

对两端各发一次 {"method":"state"}，返回体均为 4529 字节；递归比对全部叶子节点，仅 1 处不同：

路径webdesktop判读
snapshot.injection.pulls50运行期计数器：web 端已被 Agent 回合拉取 5 次；桌面端进程启动后尚未经历任何对话回合

其余关键字段两端完全相同：injection.registered=true、available=true、chars=531、activeCount=3、 storage.path 同为 C:\Users\34332\.dsh\instruction-memory\memory.json、security.boundHost=127.0.0.1、 rev=2、limits 全表一致。

含义：两端读写的是同一个存储文件，配置、集合、条目、预算在两端天然同步——这是 symlink 装载 + $DSH_HOME 解析共同决定的，不是巧合。

3.2 桌面端 origin 链路：被宿主的转发器“兜住”了

桌面端页面 origin 是 dsh-app://app，而插件的路由守卫要求 Origin 与 Host 同源。若浏览器发出真实的跨源请求， 这两个值不可能相同，理论上应当 403。实测确认了这个理论：直接构造该组合会得到 403 请求来源被拒绝：Origin 与 Host 不同源：dsh-app://app。

但真实链路不经过这一判断。桌面端的协议处理器在转发前把四个头显式删除：

被删除的请求头后果
host由 Node fetch 重新填入 127.0.0.1:19387，通过回环 Host 守卫
origin插件看到空 Origin → 跳过同源比较
sec-fetch-site避免被判为 cross-site
cookie换成宿主签发的认证 cookie

依据：DeepSeek Harness app.asar → forwardWebRequest()，for (const name of ["host","origin","cookie","sec-fetch-site"]) headers.delete(name)

同一函数还自带反向白名单：origin !== null && origin !== "dsh-app://app" 直接 403。因此桌面端实际的安全边界由宿主代理把守，插件的 Origin 守卫在这条路径上不再起作用——不是漏洞，但两端的防护层次不同（见第五节 D2）。

3.3 安全上下文能力

dsh-app 协议注册为 standard: true, secure: true, supportFetchAPI: true, corsEnabled: true。 因此桌面端页面属于 secure context，navigator.clipboard 可用， 面板的「复制诊断信息」「复制」等功能不需要走无剪贴板降级分支。

3.4 自动化回归

npm test 在工作区代码上整链通过（ALL PASS），包含 147 断言纯函数/隔离、283 断言真实路由端到端、 129 断言双半隔离加载 + i18n 键集一致性、62 断言面板真实渲染与点击。

4.3 唯一确认的交互态差异

Electron 44 把 window.prompt 换成“存在但调用即抛”的函数，typeof 仍为 'function'。 现行代码在调用点用 try/catch 判定（而非 typeof），失败时切换到面板内行内输入框。 这是布局上的局部差异（多出一个输入行），但属于正确降级，不构成一致性问题。

是否压缩传输是经宿主转发宿主对响应启用 gzip（Content-Encoding: gzip，已用插件路由实证）
bundle 缓存策略immutable强制 no-store桌面端每次启动都要重新拉取全部插件脚本
桌面端为什么强制 no-store：宿主给插件 bundle 的 URL 带一个「每次启动都变」的 revision，本意是长期缓存； 但桌面端认为「下次启动就换 revision，磁盘缓存只会白占空间」，于是在转发时把 cache-control 覆盖为 no-store。 代价是：同一台机器上，桌面端每次冷启动都要重传一遍所有插件的客户端脚本——但这是 gzip 后的约 53KB，不是 193KB，而且是本地回环。

依据：app.asar 中 PLUGIN_BUNDLE_PATH = /^\/plugins\//u 与 outgoing.set("cache-control","no-store")； gzip 比例为本地 zlib -9 实测，宿主实际级别略低，量级相同。

结论：插件本身不是加载瓶颈。11 ms 的模块加载与 0.5 ms 的注入构建，相对宿主启动（数十个插件、数百个包）可以忽略。 客户端脚本原始 201KB，但经 gzip 后仅 53KB；桌面端「不缓存」的放大效应因此从「每次重传 193KB」修正为「每次重传约 53KB 的回环流量」。

体积构成：注释 641 行、空行 116 行、代码 2,983 行；zh+en 两套词典合计约 18.6KB（9%）。 这意味着「剥离注释」最多省下一部分原始字节，gzip 后收益更小（注释压缩率极高），代价却是毁掉本仓库最核心的可读性资产——见第十节对 S1 的判断。

八、潜在问题（按严重度排序）

#严重度问题
P1 已修复 confirm 缺失时，破坏性操作的降级策略自相矛盾。 修复前：批量删除与集合删除写的是 typeof window.confirm === 'function' && !window.confirm(...)， 没有 confirm 时条件整体为 false，直接往下执行删除；版本回滚写的是 typeof window.confirm !== 'function' && return，没有 confirm 时拒绝执行。 同一类不可恢复操作，一个静默放行、一个静默拒绝。
现状：8 个调用点已统一到 askConfirm(message, unavailable)—— 持久数据类默认 deny 并提示 confirm.unavailable，丢弃草稿类用 allow； 返回值三态化，用户主动取消不再被误报成「环境不支持」；对话框存在但抛错按缺失处理。 lib/client.js；verify.mjs 新增 6 条断言守护。
P2 低 桌面端每次启动重传全部插件脚本。原始 201KB 源码，但传输时 gzip 到约 53KB， 且是本地回环，32 个插件合计并非关键路径。插件侧无低风险减重空间（见 S1 结论）。
P3 中 桌面端注入链路尚未经真实回合验证。injection.registered=true / available=true 只证明 section 注册成功， pulls=0 说明还没有任何 Agent 回合调用过它。web 端 pulls=5 是已生效的实证。 建议在桌面端发一条普通消息后复查 pulls 是否 > 0，这是唯一能证明“桌面端真的把指令送进提示词”的方式。
P4 低 窄窗口下双列表单变挤。.im-grid2 { grid-template-columns: 1fr 1fr } 无 @media 断点。 桌面端窗口常被拉窄，两列输入框会被压窄、标签与占位文本折行更频繁（具体阈值未实测，属版面推算）。两端表现相同，不是跨端差异，但影响观感。
P5 已核查 主题跟随：不存在此问题，属本报告的初版误判。 面板 CSS 通篇使用 var(--dsw-alias-bg-base, 回退值)、var(--dsw-alias-label-secondary, 回退值)、 var(--dsw-alias-brand-primary, …) 等宿主变量（--dsw-alias-*，共 9 类、数十处引用）， 深浅色会随宿主切换。
更正原因：初版只检索了 @media/max-width/grid-template-columns， 漏检 var(--…)，因而误得出「样式硬编码、未使用宿主变量」。同时把变量前缀误记成 --dsh-， 实际是 --dsw-alias-。
P6 低 两端插件生态不对等（38 vs 32），会干扰“谁更流畅”的直观感受。 宿主启动时间与内存占用主要由插件总量决定，而非本插件。做性能对比时应先对齐两侧插件集合，否则测到的是环境差异。

十、实施边界与取舍

S2 / S4：已实施

S2 是本轮唯一带行为变更的改动，也是唯一一个「不安全默认」：修复前，缺对话框的宿主里删除会不经确认落盘。 改动把 8 个调用点收口到一个三态门（yes/no/unavailable）， 按「持久数据 / 未保存草稿」区分兜底方向，并把「存在但抛错的对话框」按缺失处理—— Electron 44 给 prompt() 用的正是这种桩，原先的 typeof 判断对它完全失效。 confirmDiscard() 的既有契约（无对话框时允许取消编辑）保持不变，因为 verify.mjs 明确守护「不能把用户困在编辑器里」，且那条路径不涉及已落盘数据。

S4 是纯 CSS 新增，零逻辑风险：560px 以下表单转单列，批量标签输入独占一行。

三行结果同时证明：正常路径未被破坏（同意时确实删除并只调用一次路由）、 缺失时不再删任何东西（修复前这一行会是 2 → 1）、抛错桩按缺失处理， 且提示文案真的渲染到了面板上（说明 setError 在全部调用点作用域内可达，不是只在单元测试里成立）。

S1（客户端体积）：量化后放弃，理由如下

先把数字摆出来：client.js 201,482 B（本轮新增确认门后略增）， zlib -9 压缩后 52,961 B（26.3%）；构成是注释 641 行、空行 116 行、代码 2,983 行， 其中 zh+en 两套词典合计约 18.6KB（9%）。

三条可能路径都被否决：

  • 剥注释/空行：注释的 gzip 压缩率极高，省下的传输字节很小，代价却是拆掉本仓库最核心的可读性资产 （每个非显然决定都附「为什么」的注释，是这个项目交付质量的一部分）。
  • 拆包/压缩产物：会引入「源码 + 产物」双轨，破坏手工书写、无需构建的设计 （文件头注释即声明 “so the package needs no build step”），调试路径也随之改变。
  • 词典懒加载：只占 9%，gzip 后约 4KB，收益不抵新增的复杂度。

更关键的是前提被推翻了：初版把代价估成「每次冷启动重传 193KB」，但宿主对响应启用 gzip （已用插件路由的 Content-Encoding: gzip 实证），真实代价是约 53KB 的本地回环流量。 在本地回环上，53KB 的传输耗时在本报告的分辨率内不可测。 若仍要减重，正确的顺序是推动宿主按 revision 做 immutable 缓存，而不是让插件为宿主的缓存策略买单。

S6（双端冒烟基线）：已实施，但不进 CI

新增 live-host-smoke.mjs（npm run smoke:hosts）。它故意不接进 npm test： CI 没有桌面端，放进去必然常红，也就等于没有门禁。

一次运行测四项：state 的 p50/p95、SSE 首事件、注入注册与字符数、两端快照逐字段一致性； 另加两个立即失败条件——p50 > 50ms、以及「除 injection.pulls 外有任何字段不同」。 退出码：0 全绿 / 1 有问题 / 2 两端都连不上。支持 --web <port>、--desktop <port>、 --rounds N、--json、--require-pulls。

脚本内所有请求走 Node http 直连，不继承 http_proxy —— 这正是本轮发现 SSE 初版读数偏高的原因， 已写进文件头注释，避免下一个人用 curl 复核时再踩一次。

S3（桌面端真实回合）：工具已就位，那一条消息仍需你发

live-host-smoke.mjs --require-pulls 会在 injection.pulls === 0 时以退出码 1 失败， 并打印「该宿主尚未经历真实的 Agent 回合，注入链路未被证实」。在桌面端随便发一条消息后重跑， 从 0 变 ≥1 即闭合这个缺口——脚本无法代替你和模型说话。

十一、复核方法（可复现）

  1. 一行命令（推荐）：npm run smoke:hosts。两端在线时输出各自的 p50/p95、SSE 首事件、 注入注册与字符数、两端快照一致性，并以退出码 0/1/2 表示 全绿 / 有问题 / 两端都连不上。 加 --require-pulls 可把「桌面端从未经历真实回合」判为失败。
  2. 确认两端在线：netstat -ano | grep -E "127.0.0.1:(8080|19387)"，应各有一条 LISTENING。
  3. 手动取快照时必须绕开代理： curl --noproxy '*' -X POST http://127.0.0.1:<port>/instruction-memory/api -H "content-type: application/json" -H "origin: http://127.0.0.1:<port>" -d '{"method":"state"}'。 本机 http_proxy 指向 127.0.0.1:9708，不加 --noproxy 时连回环请求也会被代理转发， 读数会多出一次代理往返（本报告的 SSE 初版数据就是这样偏高的）。
  4. 比对两端返回体的 snapshot：预期仅 injection.pulls 可能不同。
  5. SSE：同一 URL 用 GET + Accept: text/event-stream，预期首事件为一行 retry: 5000 加一条 data: 快照。
  6. 回归：CODEBUDDY_SAFE_DELETE_ENABLED=0 npm test，预期末行 ALL PASS。
关于本次审计的边界：报告中的“一致”均指接口返回、组件树结构、样式来源、延迟量级这四个可测层面； 未包含像素级视觉回归、长时间运行的内存曲线、并发多标签页场景、以及桌面端真实回合的注入内容取证。这三项如需结论，应单独设计实验。
